## 初审结论

两个 Template Pack 已批准且没有内容漂移，不应原地修改或重新批准。Factory 的路径隔离、原子 staging、结构化文件解析、未声明文件拒绝、Artifact Library 拒绝和 Git 失败回滚均已实现；但要达到 V1.2 Stable、可创建项目并支持后续 Upgrade，仍需完成以下 6 组修正。

## 批准前必须修正

1. **Approved Pack 内容完整性**：当前 Factory 只读取 Manifest 的 `APPROVED` 字段，若模板正文被本地修改仍可能实例化。应在 `factory.toml` 外部登记 Approved Pack Digest，并在 Dry Run/Apply 前计算 path + file SHA-256；不修改 Approved Manifest。
2. **Upgrade 安装基线**：`.paos-init.json` 应使用稳定 Schema，并增加 PAOS/Factory 版本、Template Approval Reference、Template Pack Digest 与生成器标识；继续保留逐文件 SHA-256，供未来三方 Diff 和 Migration 使用。
3. **Working Pack 禁止落地**：`--provisional` 只允许 Working Pack Dry Run；当前 `--provisional --apply` 可以实际创建目录，应明确拒绝并增加负向测试。
4. **项目状态一致性**：当前 Approved Pack Apply 的 `.paos-init.json` 写为 `GENERATED`，而生成的 `PROJECT.md`/`AGENTS.md` 写为 `PROVISIONAL`。应统一为“生成后等待 Project Owner 验收”的 `PROVISIONAL`，并单独记录 Template Pack 是否 Approved。
5. **输出合同对齐**：Factory Spec 声称自动生成 Registry Candidate 和首张 Task Card，实际只生成 `.paos-init.json` 与空白 `TASKS.md` 模板。V1.2 应明确：Manifest 提供可供登记的 Project Candidate 数据，但不自动写 OS Registry；首张正式 Task Card 在项目 Objective/Scope 确认后创建，不预填虚假任务。
6. **目标路径副作用与竞态收窄**：Factory 不应隐式创建多级父目录；要求目标父目录已存在，并在 staging 最终替换前再次确认目标不存在。该检查不消除全部文件系统竞态，但可避免失败后留下额外父目录或覆盖后来出现的目标。

## 风险与回滚

- 风险：Digest 算法不稳定会误拒绝合法 Pack；必须使用排序后的相对路径与逐文件 SHA-256，并加入固定测试向量。
- 风险：`.paos-init.json` Schema 升级影响旧项目；新字段必须向后兼容，未来 Upgrader 同时识别 V0.1 与 V0.2。
- 风险：父目录必须存在会改变当前便利性；Skill 默认目标 `/Users/lotop/Projects/<id>` 前应先确认 `/Users/lotop/Projects` 存在，而不是由 Factory 隐式创建任意层级。
- 回滚：独立 Implementation Commit；失败时 Git revert，不移动 `v1.1.4` Tag，不接触已创建业务项目。
